AI SOFTWARE FACTORY

Espace_Opti

Un atelier de développement où l'humain supervise, valide et capitalise — pendant qu'une équipe d'agents IA spécialisés construit, teste et livre le code. Un template unique, dupliqué pour chaque projet, avec mémoire structurelle, documentaire et sémantique.

7 agents spécialisés 4 SOPs opérationnelles 3 couches de mémoire 2 modes de travail

01Présentation de l'espace de travail

1.1 Introduction

Espace_Opti est un espace de travail Claude Code conçu pour une vision précise : l'humain n'écrit presque plus de code — il pilote une usine logicielle. Il formule des idées, valide des plans, et capitalise des décisions. Les agents IA font le reste : ils décomposent le produit, écrivent le code, auditent leur propre travail, testent en bout de chaîne et documentent.

L'architecture repose sur un principe simple : Template + Copy.

🧬 Le template

Espace_Opti/ est le master template. Il n'est jamais modifié directement. Il contient la configuration MCP, les hooks, les scripts, les définitions d'agents, les SOPs, les skills et les slash commands.

📦 Les projets

Chaque nouveau projet est une copie dérivée du template via .\new-project.ps1 "NomDuProjet". Le projet hérite instantanément de toute l'équipe virtuelle, mais vit sa vie dans un dossier isolé avec son propre git, sa propre mémoire Pinecone, son propre graphe AST.

🧠 La mémoire

Trois couches travaillent en concert : Graphify (topologie du code), Obsidian (décisions documentées), Pinecone (recherche sémantique). L'agent retrouve le pourquoi, le où et le quoi sans jamais lire le code brut à l'aveugle.

⚡ Deux modes

LITE pour les petites modifications rapides (hooks coupés, lancement instantané). FULL pour les vraies features avec toute l'équipe. Le mode doit être proportionnel à l'impact de la modification.

02Tous les outils et mécanismes

2.1 Couche mémoire — 3 systèmes complémentaires

Chacun résout un problème différent. Ensemble, ils évitent que Claude ne cherche du code à l'aveugle ou ne réinvente des décisions déjà prises.

MÉMOIRE STRUCTURELLE

🕸️ Graphify

Analyse l'AST de 20 langages via tree-sitter et construit un graphe de dépendances. Détection de communautés via l'algorithme de Leiden, identification automatique des god nodes (fonctions les plus connectées).

  • Sortie : graphify-out/GRAPH_REPORT.md
  • Activation : hook PreToolUse automatique sur chaque Glob/Grep
  • Gain : jusqu'à 71,5× de tokens économisés sur les tâches de navigation

« Quelles sont les dépendances de sync_memory.py ? » → Claude lit le report avant de répondre.

MÉMOIRE DOCUMENTAIRE

📓 Obsidian + Local REST API

Vault de notes Markdown structuré en trois dossiers : decisions/, specs/, journal/. Accessible à Claude via le serveur MCP obsidian-mcp-server qui parle HTTPS au plugin Local REST API d'Obsidian (port 27124).

  • Lecture/écriture : via les outils mcp__obsidian__*
  • Prérequis : Obsidian lancé avec plugin Local REST API activé
  • Format : Markdown ADR (Contexte, Décision, Conséquences)

« Crée une note dans decisions/ au format ADR qui documente le choix JWT. »

MÉMOIRE SÉMANTIQUE

🔮 Pinecone

Base vectorielle serverless (AWS us-east-1). Index obsidian-memory en dimension 384, métrique cosine. Embeddings générés 100 % localement via sentence-transformers/all-MiniLM-L6-v2 — aucune clé OpenAI requise.

  • Sync : python sync_memory.py
  • Découpage : header-based via LangChain MarkdownHeaderTextSplitter
  • Auto-migration : l'index est recréé automatiquement si la dimension change

« Cherche dans Pinecone toutes les décisions sur l'authentification. »

2.2 Les 8 plugins — l'équipe virtuelle

Chaque plugin installe skills, agents et hooks qui modifient le comportement de Claude. Ils s'utilisent en langage naturel ou via slash commands.

🧠 ORCHESTRATEUR

superpowers

Rôle : orchestre la discipline TDD stricte (Red → Green → Refactor → Review).

Quand : feature non triviale qui doit être testée. Invoc : « Avec superpowers, implémente X… »

Produit : tests d'abord, implémentation minimale, refactor, review interne.

Règle cardinale : tout code écrit avant son test est supprimé. C'est voulu.

🎨 DESIGNER

frontend-design

Rôle : direction esthétique intentionnelle avant tout code UI.

Quand : composants visuels, landings, dashboards. Invoc : « Utilise frontend-design pour une page de login brutaliste… »

Produit : moodboard verbal (typo, palette, espacement) puis code React/CSS.

Empêche : le CSS générique par défaut des LLMs.

🛡️ AUDITEUR

security-guidance

Rôle : filet de sécurité automatique sur chaque Edit/Write.

Quand : HOOK AUTO aucune invocation nécessaire.

Produit : blocage + diagnostic si l'un des 9 patterns OWASP est détecté (SQLi, XSS, secrets en dur, eval, pickle…).

Bypass : possible par marqueur // security-ok: raison sur la ligne concernée.

👥 QA MULTI-AGENTS

code-review

Rôle : audit en parallèle par 4-5 sous-agents spécialisés.

Quand : avant commit. Invoc : /code-review

Produit : score de confiance pondéré (logique 30 %, types 20 %, tests 25 %, archi 25 %) + liste de blockers.

Seuil : < 80 % = PR bloquée et renvoyée pour corrections.

🧹 ANTI-BLOAT

code-simplifier

Rôle : élimine la sur-ingénierie introduite par les LLMs.

Quand : après une longue session d'itérations ou avant commit. Invoc : /simplify

Produit : wrappers inutiles supprimés, helpers d'une seule utilisation inlinés, try/except vides supprimés, commentaires paraphrasants retirés.

Invariant : ne change jamais le comportement observable — les tests passent avant et après.

🎭 E2E

playwright

Rôle : teste les parcours utilisateurs dans un vrai Chromium headless.

Quand : avant livraison. Invoc : « Utilise playwright pour tester le parcours login complet… »

Produit : tests E2E, captures d'écran à chaque étape, vérification des redirections et cookies.

Règle : un test en échec = livraison bloquée.

🏗️ ARCHITECTE

feature-dev

Rôle : décompose une feature ambiguë en plan d'implémentation ordonné.

Quand : au démarrage d'une feature non triviale. Invoc : « Lance feature-dev sur … »

Produit : plan structuré, fichiers à créer/modifier, risques identifiés, ordre d'exécution.

Complémentaire : s'utilise avant superpowers, qui prend ensuite le relais pour la phase TDD.

📦 GIT

commit-commands

Rôle : commits structurés, conformes à Conventional Commits, avec contexte.

Quand : après validation QA. Invoc : /commit

Produit : message de commit au format type(scope): description avec corps explicatif si nécessaire.

Ne fait jamais : de commit avec --no-verify sans permission explicite.

2.4 Les hooks

Un hook est un script shell exécuté par Claude Code à des moments précis du cycle de vie (PreToolUse, PostToolUse, SessionStart…). Il peut injecter du contexte ou bloquer un appel d'outil.

Hook PreToolUse — Graphify Matcher : Glob|Grep — se déclenche avant toute recherche.
Effet : si graphify-out/graph.json existe, injecte un message système rappelant à Claude de lire GRAPH_REPORT.md avant de grep le code brut.
Pourquoi : économie massive de tokens et évitement des erreurs de dépendances transitives que les LLMs ratent en lecture aveugle. 
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Glob|Grep",
        "hooks": [
          {
            "type": "command",
            "command": "[ -f graphify-out/graph.json ] && echo '...' || true"
          }
        ]
      }
    ]
  }
}

2.5 Les scripts

POWERSHELL · LAUNCHER

full.ps1

Rôle : vérifie la présence de tous les composants (hooks, MCP servers, graph, workspace) puis lance Claude Code en mode équipe complète.

Vérifications :

  1. Hook Graphify PreToolUse actif
  2. MCP servers obsidian + pinecone déclarés
  3. Knowledge graph présent (graphify-out/graph.json)
  4. _workspace/agents/ et _workspace/sops/ présents (compte les fichiers .md)

Usage : .\full.ps1 — avertit si un composant manque, demande confirmation pour continuer.

POWERSHELL · LAUNCHER

lite.ps1

Rôle : lance Claude Code sans hook Graphify, puis exécute un pipeline de sync post-session.

Séquence :

  1. Backup .claude/settings.json → .lite-backup
  2. Supprime la clé hooks du settings
  3. Lance claude
  4. À la sortie (finally block) : git diff recap → Graphify rebuild → note Obsidian auto via claude --print → sync Pinecone → cleanup
  5. Restaure settings.json depuis le backup

Garantie : le hook revient toujours, même en cas d'erreur ou de Ctrl+C.

POWERSHELL · GENERATOR

new-project.ps1

Rôle : dérive un nouveau projet depuis le template sans jamais altérer Espace_Opti.

Étapes :

  1. Valide le nom (alphanum + tirets uniquement)
  2. robocopy /E /XD /XF vers Desktop\<Nom>\ (exclut graphify-out, .git, .env, node_modules, new-project.ps1)
  3. git init + commit initial
  4. Substitue Espace_Opti → NomProjet dans CLAUDE.md
  5. Copie .env.template → .env (placeholders)
  6. Recrée graphify-out/ vide
  7. Patche les SOPs avec le nom du projet

Usage : .\new-project.ps1 "MailFlow"

PYTHON · SYNC

sync_memory.py

Rôle : vectorise les notes Obsidian dans Pinecone pour les rendre sémantiquement interrogeables.

Pipeline :

  1. Charge .env (UTF-8 BOM safe)
  2. Collecte les .md du vault
  3. Split par headers H1/H2/H3 via LangChain
  4. Charge all-MiniLM-L6-v2 (384 dim) en local
  5. Auto-migre l'index si sa dimension est incompatible
  6. Upsert par batches de 100

Coût : 0 €. Pas de clé OpenAI. Premier lancement télécharge ~90 Mo.

03Les agents en détail

Sept agents, chacun avec un rôle étroit, un budget de tokens, des triggers précis, et des règles dures. Définis dans _workspace/agents/*.md.

🏛️ Architecte

2000 tokens maxsur demande

Rôle : à partir d'un PRD validé, décomposer le produit en modules indépendants et parallélisables, avec des contrats d'interface immuables.

Skills : system-designapi-contractsdependency-mapping

Triggers : après validation du PRD (fin SOP-002).

Entrées : PRD.md, GRAPH_REPORT.md (si code existant), résultats Pinecone similaires.

Sorties : ARCHITECTURE.md + modules.json.

Règles dures :

  • Aucun module ne doit dépendre circulairement d'un autre
  • Un module fullstack est toujours scindé en frontend + backend
  • Validation utilisateur obligatoire avant que le dev parallèle démarre

Exemple prompt : « Lance l'Architecte sur PRD.md. Je veux modules.json et ARCHITECTURE.md avant de valider. »

🎨 Frontend

3000 tokens maxen parallèle

Rôle : implémente les modules owner:frontend de modules.json en respectant strictement les contrats d'interface.

Skills : reacttailwindcomponent-designaccessibility

Triggers : après validation de ARCHITECTURE.md — tourne en parallèle de Backend.

Entrées : modules.json filtré, ARCHITECTURE.md, design direction éventuelle.

Sorties : /src/components/ + /src/pages/.

Règles dures :

  • Ne jamais toucher aux fichiers owner:backend
  • WCAG 2.1 AA minimum (contrast, focus, aria-labels)
  • Si un endpoint manque, bloquer et solliciter l'Architecte

Exemple prompt : « Tu es l'agent Frontend. Lis _workspace/agents/frontend.md puis implémente les modules owner:frontend. »

⚙️ Backend

3000 tokens maxen parallèle

Rôle : implémente les modules owner:backend — routes API, schéma DB, logique métier, services.

Skills : nodejspostgresqlrest-apiauthentication

Triggers : après validation de ARCHITECTURE.md — en parallèle de Frontend.

Entrées : modules.json, ARCHITECTURE.md, recherches Pinecone sur décisions d'auth/persistance.

Sorties : /src/api/, /src/db/, /src/services/, tests sous /tests/.

Règles dures :

  • Aucun secret en dur — tout passe par variables d'environnement
  • Validation de toute entrée utilisateur avant DB
  • Passwords : bcrypt/argon2 minimum, jamais en clair
  • Tests écrits AVANT l'implémentation (TDD style superpowers)

🛡️ Sécurité

500 tokens maxPreToolUse auto

Rôle : intercepte chaque Edit/Write et scanne le new_string contre 9 patterns OWASP avant écriture disque.

Skills : owasp-top10injection-preventionauth-security

Triggers : hook PreToolUse automatique — jamais invoqué à la main.

Entrées : contenu de l'Edit/Write courant, chemin cible.

Sorties : APPROVED ou BLOCKED avec pattern, ligne, fix suggéré.

Les 9 patterns : SQLi · Shell injection · XSS · eval/exec · secrets en dur · path traversal · désérialisation unsafe · redirection ouverte · crypto faible.

Bypass légitime : marqueur # security-ok: raison sur la ligne concernée.

🧑‍⚖️ QA Review

4000 tokens maxaprès chaque module

Rôle : lance 4 sous-agents en parallèle sur le diff d'un module terminé et calcule un score de confiance pondéré.

Skills : code-analysistest-coveragebusiness-logic-validation

Sous-agents :

  • logic-reviewer (30 %) — cas limites, invariants
  • type-reviewer (20 %) — any/unknown, null safety
  • test-reviewer (25 %) — % couverture + happy path + erreurs
  • arch-reviewer (25 %) — respect des contrats, pas de fuites inter-modules

Politique : score ≥ 80 → passe au Simplifier. Score < 80 → renvoie à l'agent d'origine avec blockers.

Sortie : REVIEW_REPORT.md avec score ventilé.

🧹 Simplifier

2000 tokens maxaprès QA ≥ 80

Rôle : élimine le bruit structurel introduit par les LLMs sans changer le comportement observable.

Skills : refactoringdry-principlecomplexity-reduction

Heuristiques : wrappers 1-call inlinés, classes mono-méthode devenues fonctions, try/except vides supprimés, commentaires paraphrasants supprimés, variables intermédiaires inlinées, paramètres inutilisés supprimés.

Invariant : les tests doivent passer avant ET après. Si un test casse → rollback immédiat.

Sortie : SIMPLIFICATION_REPORT.md avec suppressions, métriques LOC, delta.

🎭 Playwright

2000 tokens maxavant livraison

Rôle : dernière barrière avant livraison — valide les user stories du PRD dans un vrai Chromium headless.

Skills : browser-automationform-testingscreenshot-capture

Triggers : après le Simplifier, avant SOP-004.

Entrées : PRD.md, application démarrée localement.

Sorties : TEST_REPORT.md + screenshots/YYYY-MM-DD/<story>/step-N.png.

Règle : un test en échec = livraison bloquée. Pas de workaround sans validation explicite.

04Les SOPs — Standard Operating Procedures

Quatre procédures formelles qui définissent l'ordre exact des opérations. Pas de variation « on s'adapte » — si une SOP dit « validation utilisateur obligatoire », rien ne passe sans validation.

SOP-001 — Lancer un nouveau projet
L'utilisateur tape : .\new-project.ps1 "NomProjet"
Robocopy Espace_Opti → Desktop\NomProjet\ (exclusions appliquées)
git init + commit initial + patch CLAUDE.md
Lance SOP-002 à l'ouverture de Claude Code dans le nouveau dossier
🛑 Attendre la validation du PRD avant toute génération de code

Règles : ne jamais modifier Espace_Opti directement — chaque projet a son propre index Pinecone <nom-projet>-memory.

SOP-002 — Création du PRD
Phase 1 — Idée brute en langage naturel
Claude reformule en 5 lignes → demande confirmation
Phase 2 — Questionnaire guidé (8 questions, une par une)
Problème · Cibles · MVP · V2 · Stack · B2B/B2C · Délai · Contraintes
Phase 3 — Génération PRD.md structuré
Executive Summary · User Stories · FR · TR · Constraints · MVP · V2 · Metrics
🛑 Validation utilisateur obligatoire avant SOP-003

Les 8 questions dans l'ordre :

  1. Quel est le problème principal résolu ?
  2. Qui sont les utilisateurs cibles ?
  3. Quelles sont les 3 fonctionnalités essentielles (MVP) ?
  4. Quelles sont les fonctionnalités secondaires (V2) ?
  5. Stack technique préférée ?
  6. Le projet est-il B2B, B2C ou interne ?
  7. Quel est le délai souhaité ?
  8. Y a-t-il des contraintes (budget, langue, accessibilité) ?
SOP-003 — Développement parallèle
1. Architecte → ARCHITECTURE.md + modules.json
🛑 Validation utilisateur de l'architecture
2a. Frontend
composants UI + pages
2b. Backend
API + DB + services
🛡️ Sécurité surveille chaque Edit/Write en temps réel (hook auto)
3. QA Review après chaque module DONE
Score ≥ 80 ? → étape 4. Sinon → retour à l'agent.
4. Simplifier — élimine le bruit
5. Playwright — tests E2E sur les user stories
6. → SOP-004 Livraison

Règles de parallélisme : un agent = un terminal ; agents isolés par files_owned dans modules.json ; contrats d'interface immuables ; verrouillage git optimiste sur modules.json.

SOP-004 — Livraison
Checklist : tous modules DONE · QA ≥ 80 · Playwright 0 fail · 0 vuln · Simplifier passé
1. Génération DEPLOYMENT.md
2. Note Obsidian ADR : decisions/YYYY-MM-DD-<projet>-livraison.md
3. python sync_memory.py + rebuild graphe
4. git commit feat: <projet> v1.0.0 - MVP livré + tag v1.0.0
✅ Projet livré — Pas de git push sans ordre explicite

5.6 LITE vs FULL — arbre de décision

Est-ce que la modification mérite une discipline complète ?
⚡ LITE MODE

08Tips, avertissements et maintenance

⛔ Avertissements critiques

Ne jamais modifier Espace_Opti directement Toujours passer par .\new-project.ps1 pour dériver un projet. Une modif dans le template se propage silencieusement à tous les futurs projets et devient impossible à tracer.
Le fichier .env ne doit JAMAIS être commité Il contient les clés Pinecone et Obsidian. Vérifie que .gitignore exclut .env dans chaque projet dérivé. Seul .env.template est commité.
Obsidian doit être lancé pour que le MCP fonctionne Le serveur obsidian-mcp-server parle HTTPS à Obsidian sur 127.0.0.1:27124. Si Obsidian est fermé, toute commande MCP mcp__obsidian__* échouera avec connection refused.
Après setx, redémarre le terminal setx ne met à jour que les futurs processus. Ferme complètement VS Code (pas juste l'onglet terminal) et relance-le.
BOM encoding avec PowerShell Set-Content Set-Content -Encoding UTF8 écrit un BOM UTF-8 que certains parsers (python-dotenv notamment) interprètent comme un caractère du premier nom de clé. Préfère [System.IO.File]::WriteAllText($path, $content, [System.Text.UTF8Encoding]::new($false)) pour écrire sans BOM, ou charge avec encoding='utf-8-sig' côté lecture.

💡 Tips & astuces

1 · Un agent par terminal

Ne mets jamais deux agents dans la même session Claude Code. Le partage de contexte les fait dériver — chacun doit avoir son périmètre strict.

2 · Toujours lire GRAPH_REPORT.md avant de grep

Le hook le fait pour toi, mais tu peux aussi le demander explicitement : « Quels god nodes impacte ce changement ? ». Tu gagnes des tokens et tu attrapes les dépendances transitives.

3 · Pinecone avant Graphify

Avant toute feature, commence par « Cherche dans Pinecone les décisions sur X ». Tu retrouves le pourquoi avant de chercher le où.

4 · Un commit = un code-review

Ne pousse jamais du code sans /code-review. Même si tu penses que c'est trivial. Les régressions cachées sont la raison d'être de ce pipeline.

5 · Note Obsidian après chaque décision

Toute décision prise en session (« on garde JWT plutôt que sessions ») = une note ADR dans decisions/. Sinon elle disparaît avec le contexte.

6 · Lance sync_memory.py en fin de session

Le pipeline .\lite.ps1 le fait pour toi automatiquement. En FULL mode, fais-le à la main avant de fermer le terminal.

7 · LITE pour tout ce qui prend < 5 minutes

Renommer une variable, changer une couleur, corriger un commentaire : LITE. Tu gagnes 30-60 secondes par invocation et tu évites de saturer le contexte.

8 · Utilise /context avant les longs prompts

Vérifie combien de tokens tu as consommés. Si tu es à 70 % + et que la tâche est longue, démarre une nouvelle session plutôt que risquer une troncation.

9 · Esc Esc sauve des vies

Tu as supprimé un message par erreur ? Double-Escape le restaure. Note-le dans ton muscle memory.

10 · Shift+Tab = Plan mode pour les features

Plan mode empêche Claude d'écrire quoi que ce soit tant que tu n'as pas validé le plan. C'est la version intégrée de la phase 1 de SOP-002. Utilise-la dès que la tâche dépasse « corriger un bug évident ».

11 · modules.json est la source de vérité

En développement parallèle, si un agent ne sait pas s'il doit toucher à un fichier, il lit modules.json. Point final. Pas de négociation en session.

12 · Un test cassé = un commit révert, pas un fix

Si le Simplifier casse un test, on rollback — on ne corrige pas le test. Le Simplifier doit être transparent sur le comportement observable.
